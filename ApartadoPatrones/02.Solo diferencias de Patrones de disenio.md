# 4. Patrones que suelen confundirse

| #   | Categoría                       | Patrones que se confunden                        | Por qué se confunden                                                 | Pregunta clave para decidir                                                                  | Elegiría...                                                                                                                                                      |
| --- | ------------------------------- | ------------------------------------------------ | -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A   | Creacionales                    | Factory Method _vs_ Abstract Factory             | Ambos crean objetos y desacoplan al cliente de clases concretas.     | ¿Necesito crear un producto puntual o una familia de productos relacionados?                 | **Factory Method** si una subclase decide qué producto crear. Abstract Factory si creo familias compatibles.                                                     |
| B   | Creacionales                    | Builder _vs_ Factory Method / Abstract Factory   | Todos participan en la creación de objetos.                          | ¿El problema es qué objeto crear o cómo construirlo paso a paso?                             | **Builder** si el objeto es complejo, con muchos pasos o configuraciones. **Factory / Abstract Factory** si el foco es elegir el tipo de objeto.                 |
| C   | Estructurales                   | Adapter _vs_ Decorator                           | Ambos pueden envolver un objeto.                                     | ¿Estoy adaptando una interfaz incompatible o agregando responsabilidades?                    | **Adapter** si traduzco una interfaz. **Decorator** si agrego funcionalidad manteniendo la interfaz.                                                             |
| D   | Estructurales                   | Composite _vs_ Decorator                         | Ambos usan composición y pueden tener estructuras parecidas.         | ¿Estoy armando una estructura árbol parte-todo o agregando capas de funcionalidad?           | **Composite** si hay hojas y compuestos tratados uniformemente. **Decorator** si agrego extras dinámicamente.                                                    |
| E   | Comportamiento _vs_ Estructural | Chain of Responsibility _vs_ Decorator           | Ambos pueden formar una cadena de objetos.                           | ¿La cadena decide quién atiende la solicitud o suma funcionalidades por capas?               | **Chain of Responsibility** si la solicitud pasa hasta que alguien la maneje. **Decorator** si cada capa agrega comportamiento.                                  |
| F   | Comportamiento                  | Template Method _vs_ Strategy                    | Ambos resuelven variaciones de algoritmos.                           | ¿El algoritmo cambia completo en runtime o solo cambian pasos dentro de una estructura fija? | **Strategy** si quiero intercambiar algoritmos. **Template Method** si la estructura general es fija y varían pasos.                                             |
| G   | Comportamiento                  | Observer _vs_ Strategy / Chain of Responsibility | Puede confundirse cualquier comunicación entre objetos con Observer. | ¿Hay un objeto observado que notifica a varios suscriptores?                                 | **Observer** si hay relación uno-a-muchos con notificación. **Strategy** si se elige algoritmo. **Chain of Responsibility** si se pasa una solicitud por cadena. |
| H   | Estructurales                   | Facade _vs_ interfaz gigante                     | Ambos pueden aparecer como una clase de acceso a muchas cosas.       | ¿La clase simplifica el subsistema o se volvió una mega-API?                                 | **Facade** si ofrece pocas operaciones claras. Si tiene demasiados métodos públicos, conviene dividir en varias fachadas.                                        |
| I   | Creacionales / Diseño           | Singleton _vs_ Static / variables globales       | Ambos dan acceso global o centralizado.                              | ¿Necesito una única instancia controlada o solo funciones o valores de clase?                | **Singleton** si debe existir una única instancia. **Static** si no necesito instancia ni polimorfismo.                                                          |
| J   | Comportamiento                  | State _vs_ Strategy                              | Estructuralmente se parecen: contexto + objeto delegado.             | ¿Cambio la forma de hacer algo o el objeto cambia porque está en otro estado?                | **Strategy** si son distintas maneras de hacer. **State** si son distintas maneras de estar.                                                                     |

# 5. Reglas express para parcial

## 5.1 Por categoría

- Crear objetos → **Singleton / Factory Method / Abstract Factory / Builder**
- Organizar o envolver objetos → **Adapter / Composite / Decorator / Facade**
- Comunicación o comportamiento variable → **Strategy / Observer / Chain of Responsibility / Template Method**
- Estados internos del objeto → **State** **[EXTRA]**

---

## 5.2 Por palabras clave

| Palabra o idea del enunciado            | Patrón probable             |
| --------------------------------------- | --------------------------- |
| Única instancia / punto global          | **Singleton**               |
| Subclases deciden qué crear             | **Factory Method**          |
| Familias de productos relacionados      | **Abstract Factory**        |
| Construcción paso a paso                | **Builder**                 |
| Interfaz incompatible / sistema legado  | **Adapter**                 |
| Árbol / parte-todo / hojas y compuestos | **Composite**               |
| Agregar responsabilidades por capas     | **Decorator**               |
| Simplificar subsistema complejo         | **Facade**                  |
| Algoritmos intercambiables              | **Strategy**                |
| Uno-a-muchos / notificar suscriptores   | **Observer**                |
| Cadena de handlers / pasamanos          | **Chain of Responsibility** |
| Estructura fija con pasos variables     | **Template Method**         |
| Comportamiento según estado interno     | **State**                   |

# 6. Glosario de conceptos ampliados

## Mockear

**[AMPLIACIÓN]**  
Mockear es simular un objeto real con uno falso para poder probar una parte del sistema sin depender de componentes externos.

Ejemplo simple:

- En vez de consultar una base de datos real, uso un objeto falso que devuelve datos ya preparados.
- En vez de usar un servicio real de pagos, uso un objeto falso que responde “pago aprobado”.

Sirve mucho para pruebas.

---

## Overhead

**[AMPLIACIÓN]**  
Overhead es el costo extra que aparece por agregar una capa, una abstracción o una delegación.

Puede ser:

- más memoria;
- más objetos;
- más llamadas entre clases;
- más complejidad de lectura;
- más mantenimiento.

No siempre es malo. A veces se acepta ese costo para lograr flexibilidad, reutilización o desacoplamiento.

---

## Runtime

**[AMPLIACIÓN]**  
Runtime significa “tiempo de ejecución”, es decir, mientras el programa está corriendo.

Ejemplo:

- En Strategy, puedo cambiar el algoritmo durante la ejecución.
- En Decorator, puedo agregar nuevas capas durante la ejecución.
- En State, el objeto puede cambiar su comportamiento al cambiar su estado interno.

---

## API

**[AMPLIACIÓN]**  
API es una interfaz de comunicación. En Programación II puede entenderse como el conjunto de métodos o servicios que una clase, módulo o sistema ofrece para ser usado por otros.

---

## God object

**[AMPLIACIÓN]**  
Un God object es una clase que hace demasiado. Suele tener muchas responsabilidades, muchos métodos y mucho conocimiento del sistema.

Es una señal de mal diseño porque rompe la separación de responsabilidades.

---

## Leak

**[AMPLIACIÓN]**  
Leak significa fuga. En Observer, puede pasar si un observador queda suscripto cuando ya no debería estarlo. El Subject sigue guardando su referencia y eso puede traer problemas.

---

## Middleware

**[AMPLIACIÓN]**  
Middleware es una capa intermedia que procesa una solicitud antes de llegar al destino final. Se parece mucho a Chain of Responsibility cuando una request pasa por varios handlers.

---

## Hook

**[AMPLIACIÓN]**  
Un hook es un método que permite personalizar una parte de un algoritmo. En Template Method, un hook puede tener comportamiento por defecto y una subclase puede redefinirlo si lo necesita.

---
